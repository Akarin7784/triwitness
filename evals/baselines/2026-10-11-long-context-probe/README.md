# 2026-10-11 长上下文实测：deepseek-flash 在 ~200K / ~500K / ~900K 输入下的召回与首字延迟

- 时间：2026-10-11（周日）20:38–20:41 北京时间，空闲时段（非高峰价）；全部 21 次调用 `peak=false`。
- 模型：只用 deepseek-flash（服务端回报 `deepseek-flash`）；每次调用都记入本机账本（类别 `long_context_probe`）。
- 脚本：`scripts/probe_long_context.py`（`TW_LLM_MODE=live`）。合成文本按种子（= 档位目标 token 数）确定性生成，不入库；原始数据见 `results.json`。
- 目的：验证默认 harness `long-context-1m.yaml` 的约 950K 工作预算（Executor 输入硬上限 951,582）在召回与延迟上是否站得住。

## 方法

- 草堆：合成的 Python 仓库源码拼接（类 / 方法 / 文档串），实测约 3.62 字符 / token。每个模块里还有 1–3 个与针同形的干扰函数
  （`def get_xxx_yyyy() -> int: return 5 位整数`），所以模型不能靠“找唯一的那个数字”来答。
- 针：5 个唯一函数名 → 5 位整数，分别放在 5% / 25% / 50% / 75% / 95% 深度。
- 每档 7 次调用，前缀完全相同、只换末尾问题：
  1. 冷启动单针（50% 深度，缓存未命中）→ 冷首字延迟；等 8 秒让缓存落盘；
  2. 4 次热缓存单针（其余深度）→ 热首字延迟；
  3. 1 次 5 针全列（热）；
  4. 1 次单针，思考模式 effort=high（与 Executor 同档）。
- 首字延迟（TTFT）= 发出请求到收到第一个流式增量（推理或正文）的时间，从本机测，含网络往返。
- 判分：答案里出现正确的 5 位整数就算对（单针回答都只有这个整数）。

## 结果

| 档位 | 实际输入 token | 单针召回（非思考） | 5 针全列 | 思考模式单针 | 冷 TTFT | 热 TTFT（中位 / 区间） | 思考 TTFT | 冷调用费用 | 热调用费用 |
|---|---|---|---|---|---|---|---|---|---|
| ~200K | 188,329 | 5/5 | 5/5 | 1/1 | 4.8 s | 2.8 s（2.4–3.3） | 5.4 s | ¥0.188 | ¥0.0039 |
| ~500K | 500,094 | 5/5 | 5/5 | 1/1 | 10.5 s | 4.0 s（3.4–5.0） | 10.9 s | ¥0.500 | ¥0.0103 |

\* 900K 的第 2 次调用（冷启动后 8 秒）只命中 511,360 / 899,613（缓存还没建完），TTFT 12.0 s、¥0.398；不计入热中位数。

合计：召回 33/33（单针 15 + 全列 15 + 思考 3），全部 `finish_reason=stop`。账本增量 **¥3.72**（21 次调用）。

## 发现

1. **召回**：到约 900K 输入，5 个深度的精确查找全对，没有“中段遗忘”。注意这是字面查找类任务（按唯一函数名找值），
   比真实编码任务的跨文件推理容易得多，只能证明“放得下、找得到”，不能证明“900K 上推理质量不降”。
2. **预填充吞吐近似线性**：冷 TTFT 约 4.8 / 10.5 / 18.8 s，即约 40–48K token/s，没有超线性恶化。
   一轮从零开始的 900K 冷请求要等约 19 s。
3. **热缓存很关键**：900K 热请求 TTFT 约 5 s、单次 ¥0.018（命中价 1/50）；冷请求 ¥0.90，是热请求的约 50 倍。
4. **缓存落盘需要时间**：900K 冷请求之后 8 秒再发，只命中约 57%（511K），多花 ¥0.38。Agent 循环里两轮之间通常有工具执行时间，
   影响不大；但“压缩 / 清理后紧接着连续调用”会吃到这个代价。
5. **思考 / 非思考模式不共享缓存**：同一前缀，思考模式请求命中 0（三档都一样），每次都按冷价计费。
   推论：同一份长前缀不要在思考 / 非思考之间来回切换；Executor 全程思考模式（effort=high），不受影响；
   Summarizer 等非思考角色对 Executor 转录本的调用本来就是一次性的冷请求，按冷价计入成本模型。

## 对 950K 默认值的结论

站得住，保持 `long-context-1m.yaml` 不变（工作预算 auto → 951,582；清理 50%→25%；压缩 75%）。
理由：900K 时召回无损；热请求延迟约 5 s、¥0.018 / 轮，可接受；冷请求约 19 s / ¥0.9 是一次性代价，
而清理阈值（约 475K）意味着大多数轮次的上下文远小于 900K。待办：用真实编码任务（W2 dev 集）做 128K vs 950K 的消融，
验证推理质量与总成本，而不只是查找召回。
