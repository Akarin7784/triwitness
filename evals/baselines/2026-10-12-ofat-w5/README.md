## 结论

1. **解决率：dev 15 在这些旋钮上分不出差别，而且原理上也分不出来。** 12 题所有配置都能做、3 题所有配置都做不了，没有一题“有的配置能做、有的不能”。
   最好情况也只能多解出 3 题（+20 pp）；即使某个配置 15/15，McNemar b=0、c=3，精确 p = 0.25，也不显著。每题 1 次时配对 MDE ≈ 32 pp（20% 不一致对假设）。
   把同一套题重复 3 次也只能看出每题的稳定性，不会改变这个上限。**所以这一轮只能作探索性结论，不能写“更好 / 更差”。**
2. **花费：唯一站得住的差别是 thinking=high 和 Planner 贵了约 3.3–3.4 倍**（逐题配对 bootstrap 区间都不含 0），解决率一点没涨。
   thinking=high 输出 tokens 是基线的 3.8 倍、步数 +10；Planner 多出约 ¥1.5，主要是 Planner 自己的思考输出（163K reasoning tokens）。
3. **thinking=low 便宜、步数少一点**（20.7 对 23.9，花费 +¥0.004/题，区间含 0），轨迹确认思考确实开了（51K reasoning tokens），但假成功多 1 次、解决率没变，不建议据此改默认。
4. **repro-first 最便宜**（¥0.040/题，比基线略低，区间含 0），15 题都调用了 `submit_repro`。当前默认 harness `long-context-1m` 就继承 repro-first，这一臂的结果支持维持现状。
5. **上下文策略在 128K 下几乎没有被触发**：基线（清理 + 压缩）15 题 0 次清理、0 次压缩，单次调用最大输入 42K，还没到清理线（0.6 × 128K ≈ 77K）。
   none / compact-only / clear-only 三档实际上跑的是同一套行为；clear-only 贵一点来自 crosstl 那次跑满 100 轮，是 agent 的随机性，不是策略差别。缓存命中四档都在 97% 左右。
6. **在 1M 默认档（long-context-1m，工作预算 ≈ 951,582）下，这几档上下文策略在 dev 上没有区别**：全部 4138 次调用里单次最大输入是 101K（thinking=high），
   远低于 1M 档的清理线 ≈ 476K、压缩线 ≈ 714K，所以任何一档都不会触发清理或压缩，行为完全相同。要比较上下文策略，得换成真正长的任务（ext 题集里的大仓库题，或 `context-stress` harness），dev 15 测不出来。

## 建议

- **默认配置不改**：执行器维持 flash 非思考；harness 维持 long-context-1m（含 repro-first）；工具集维持现在 10 个（minimal-4 / repo-map 没带来收益）；Planner 维持默认关（只在 `orchestrated-1m` 里开）。
- **thinking=high 和 Planner 不要默认开**：3 倍多的成本，dev 上没有任何解决率收益。如果要再测它们，应该放在更难的题上。
- **下一轮消融换题集，而不是加重复次数**：dev 15 已经饱和（12 必过 + 3 必挂），重复 3 次（约 ¥33）也测不出差别。建议用 `ext-reserve` 59 题做调参（`ext` 50 题留给冻结后的终测，`test` 只出报告），
  先只比 2–3 个臂（基线 / thinking=low / Planner），约 ¥8–15。上下文策略单独用长任务测。
- **补齐 `.z06` 后结论不变**。补上的几臂：thinking-high 共 3 次清理 / 1 次压缩（128K 档，最大输入 101K）；thinking-low、minimal-4、repo-map 都是 0 次清理 / 压缩。
  工具使用：minimal-4 没有 grep / run_tests，bash 调用 336 次（基线 162），步数和花费略多；repo-map 有 12/15 题调用了 `repo_map`（共 12 次），没带来解决率或成本变化。
