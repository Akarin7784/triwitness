# 问答（按 04 §11 逐题，W8-08 草稿）

出处见 [README.md](README.md) 速查表；终测（W8-01）数字已回填，出处 `evals/baselines/2026-10-12-final-w8/README.md`。原则：每个回答 = 设计 + 一个实测数字 + 一个坦白的局限。

## 11.1 Agent Loop 与工具

**Q：从 Issue 到 PR 的完整链路？**
编排器跑显式状态机（`core/state_machine.py`，非法迁移直接抛异常，可从事件重放）：接收 → 准备沙箱 → Planner → （计划确认）→ 复现 → Executor 修复 → Verifier → Reviewer →（返工 ≤2 轮）→ 打包 → 等人批准 → 推分支开 PR → 看 CI。三条原则：状态迁移只由编排器做；`finish` 只是声明，由 Verifier 复核；推送 / 开 PR 带幂等键（`<run_id>:open_pr:0`），重复执行返回同一个 PR。v1 默认只出本地分支 + `pr.md`，开 PR 需人确认（不做 GitHub App）。

**Q：工具调用失败 / 输出格式不稳定？**
工具错误分类返回给模型（非零退出、超时、匹配失败、schema 错误）；结构化输出走“auto → 修复 ×2 → 正文抽 JSON”降级链。DeepSeek 思考模式不接受强制 `tool_choice`，所以评审的最后一次调用关思考再强制 `submit_review`。数字：W3 模型档 144 次判读全部走 tool_call，0 次修复、0 次解析失败（`2026-10-10-w3-verifier/analysis.md` §4）。

**Q：工具多了是不是更好？**
OFAT 里“极简 4 工具 / repo-map”和基线逐题结果完全一样（`2026-10-12-ofat-w5/report.md`）——但 dev 15 已饱和，我只能说“没看出差别”，不能说“没用”。

## 11.2 上下文工程

**Q：长会话越来越大怎么办？**
面向 1M 窗口：工作预算 ≈ 窗口 − 输出预留 − 3% ≈ 950K；50% 时批量清理较早的可重取工具结果、清到 25%；75% 才摘要压缩，压缩前先把失败原因写进 NOTES，压缩后重读最近改过的文件，连续两次无效压缩就停。理由是价格：DeepSeek 缓存命中价是未命中的 1/50（`configs/pricing.yaml`：0.02 vs 1.0 元/百万），只追加很便宜，改写历史会让之后全部未命中。长上下文探针约 900K 针召回全对，冷首字 19 s、热 5 s（`2026-10-11-long-context-probe/`）。

**Q：上下文和成本的关系？**
W2 基线每题平均输入 214 万 token，但缓存命中 97.2%，所以只要 ¥0.233/题；TB2 r3 命中 98.1%（`2026-10-10-w2/analysis.md`、`2026-10-12-harbor-tb2-r3/README.md`）。局限：W2 失败里 11 个是先撞 3M 输入上限——问题不在压缩而在“探索太久不动手”，这推动了 repro-first。

**Q：怎么判断上下文被污染？**
工具返回、Issue 正文、MCP 返回一律包成不可信块；死循环检测三种信号（重复动作 / 连续失败 / 无进展）分级处理；子角色只通过编排器传结构化结果。

## 11.3 多 Agent 编排与评审

**Q：四个角色会不会只是多花钱？**
用数据回答：OFAT 里单独加 Planner，dev 上解决率不变、成本 ¥0.143 vs 基线 ¥0.042/题（约 3.4 倍）（`2026-10-12-ofat-w5/report.md`）。所以默认 harness 仍是单 Executor，终测 test 35 配对：完整流水线 54.3% vs 45.7%，3:0 但 McNemar p = 0.25 不显著，同价成本约 2 倍（Planner 占一半）——所以默认仍是单 Executor，流水线留给难题。

**Q：为什么评审要换模型？你做了吗？**
没做跨厂商（预算只够 DeepSeek，ADR-0002），改成同厂商异构变体并如实标 `vendor_policy=single_vendor`。在 40 道注入缺陷题、每臂 120 次上：清单式非思考 vs 对抗式思考检出率差 +0%（按题聚类 95% −18%～+18%），没下结论 20% → 7%，¥0.030 vs ¥0.097/次 → 默认 checklist（ADR-0007，`2026-10-12-reviewer-ablation/`）。另外“没结论 ≠ 通过”：仍无结论就标 `reviewer_inconclusive`、风险下限 L2。

**Q：子 Agent 怎么通信？**
只经编排器传结构化结果（`submit_plan` / `submit_review`），没有共享可写通道；跨 agent 委托内容会做注入扫描（红队 cross_agent 4 条全挡）。

## 11.4 验证器与评测

**Q：怎么防 Agent 改测试？**
隐藏测试不进沙箱；Grader 只应用非测试改动；防作弊规则把“削弱 / 跳过 / 恒真断言 / 改测试基础设施”记为篡改，“改已有测试期望”单列人审。W2 复核：篡改 9 → 3，另 6 次改写里 4 次失败——“改测试迁就实现”是虚假成功的强信号（`2026-10-10-w2/analysis.md` §3）。

**Q：验证器到底有没有用？**
48 个补丁、真值 28 解决 / 8 假成功：判 pass 精确率 72% → 85%（确定性）→ 89%（+模型），召回 75% → 61% → 57%，假成功拦下 0 → 5 → 6（`2026-10-10-w3-verifier/analysis.md`）。反直觉：Agent 自写复现测试一个假成功都没拦住；拦住的是声明审计 4、防作弊 1、模型 1。放过的 2 个里模型其实写出了风险却还给 pass——规则复核后精确率 88%、错判 L3 归零（`2026-10-10-w3-rules/analysis.md`）。

**Q：评测集怎么建、怎么防污染？**
从 SWE-rebench 挖题、Harbor 兼容格式、null=0 / oracle=1 跑 3 次去抖；dev / test 冻结带 digest，test 只出报告；匿名任务 ID、清洗 Issue 里的提交 / PR 链接与 SHA、禁用 git hooks、开网时屏蔽代码托管域名。新旧题 45% vs 55%，差在 CI 内，看不出污染效应（n 小，如实分报）。

**Q：怎么证明 A 比 B 好？**
同批任务配对：McNemar 精确检验 + Holm 校正 + 按题聚类 bootstrap，区间不含 0 才写“更好”（`eval/ablation.py`）。坦白：n=35 可检出差异约 25–30 个百分点；OFAT 10 个配置逐题完全相同，结论只能是“dev 饱和”。TB2 r2→r3 +6.7pp 也写的是“在噪声里”。

## 11.5 持久化执行、HITL、失败恢复

**Q：怎么暂停和恢复？**
每个 Executor 步骤是检查点；`--resume` 从 `trajectory.jsonl` 重放模型上下文（命中前缀缓存），检查点之后不重跑；有副作用的工具先写预写日志，续跑时列出“已发起、需先确认的外部操作”。有 SIGKILL 崩溃续跑的子进程测试。没用 Temporal：单机进程内状态机 + 事件日志已够，少一个依赖。

**Q：死循环怎么防？**
三种信号 + 三级处理；外部任务另加超时守卫（拦近似重跑的超时命令、按剩余墙钟压 timeout）。TB2 overfull-hbox 从 1/3 → 3/3（`2026-10-12-harbor-tb2-r3/README.md`）。

**Q：哪些操作要人批？审批疲劳？**
按风险分级：L2 以上计划、改依赖声明、改 CI 配置必须人确认，不交给自动审核模型；终端非交互一律拒绝；评测模式自动批准保证可复现（只限评测）。

## 11.6 模型路由与成本

**Q：多模型后端怎么抽象？**
自研薄适配层（`transport: direct`，没上 LiteLLM）处理思考模式、推理内容回传、tool_choice 限制、用量字段、served_model 记录；模型白名单只有 deepseek-flash（永不 v4-pro）。跨厂商在接口上留了，没接（资金）。

**Q：怎么控成本？**
缓存优先的上下文设计、按角色分档（评审非思考）、空闲时段跑大评测、事前估算、每条调用记本地账本。北极星是“每个已解决任务的成本”：W2 test ¥0.510/解决；评审默认改 checklist 直接省 2/3。0.3.2 起去掉了金额硬上限（产品决定），只保留防失控的轮数 / 时长 / token 上限。

**Q：线上问题怎么定位？**
每个模型调用、工具调用写 `tw-events/1` 事件（完整请求 / 响应存 artifacts，脱敏），可选 OTel GenAI span 导出；`tw diag export` 打脱敏诊断包。没接 Langfuse。

## 11.7 Skill 与记忆

**Q：Skill 和 MCP 的边界？**
MCP 连外部系统，Skill 打包做事方法（Agent Skills 规范）；上下文里只放 name + description，需要时 `load_skill` 读正文。记忆按仓库存在 `~/.triwitness/memory/`，不写进用户仓库。

**Q：自进化怎么证明没越改越差？**
只从验证通过的 run 蒸馏、只进候选区；Skill 要过 A/B 门禁（held-out、有 / 无 Skill × 2 配对，提升且成本 ≤ +5% 才合入），上线后真正读过正文的样本 ≥ 8 且比门禁低 15pp 以上自动回滚。坦白：门禁真跑（约 ¥4）还没做，目前只有静态检查 + 单测；桌面端已能显示“本次用了哪些记忆”。

## 11.8 安全网关

**Q：MCP 的风险？**
工具描述注入、rug-pull（工具元数据变脸）、令牌过宽。网关做白名单 + 版本固定 + 元数据指纹，第 N 次变脸隔离，返回包标不可信。

**Q：为什么“密钥不进沙箱”还不够？**
被注入的 Agent 还能合法滥用已授权的 API。所以沙箱里只有占位符，网关按域名 + 方法 + 路径注入真凭证；参数级策略 fail closed（分类器不确定就拒）；破坏性外部操作延迟可撤销；git 只允许推 `tw/*`。

**Q：效果怎么衡量？**
红队 39 条（含 SSRF 5、跨 agent 4）：开网关 39/39 挡住，关网关 35/39 得逞，开臂额外延迟 p50 ≈ 9 ms（`2026-10-12-redteam-gateway/README.md`）。坦白：这是确定性路径；“真 Agent 读到投毒后会不会照做”的端到端红队还没跑，误报率 / 效用损失也还没测。
